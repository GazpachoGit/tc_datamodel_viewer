# Подход к проектированию

## Назначение

Браузерное приложение строит интерактивную UML-подобную диаграмму классов
на основе XML-модели Teamcenter и показывает свойства выбранного атрибута.
Функциональные требования описаны в [requirements.md](./requirements.md),
рекомендуемая модель данных — в [model.md](./model.md).

## Технологии

- **TypeScript** — типизированная модель данных и логика приложения.
- **React и Vite** — интерфейс и сборка приложения.
- **React Flow** — интерактивная диаграмма с пользовательскими узлами классов
  и связями наследования.
- **ELK.js** — автоматическая иерархическая раскладка диаграммы.
- **DOMParser** — разбор XML в браузере с учётом пространства имён Teamcenter.
- **js-yaml** — разбор [mapping.yaml](./mapping.yaml), включённого в
  сборку; отдельная загрузка файла маппинга пользователем не требуется.
- **Обычный CSS** — стилизация интерфейса. Tailwind и отдельная библиотека
  компонентов пока не нужны; React-компоненты создаются по мере необходимости.

Приложению не нужны серверная часть, Tauri или Electron. XML обрабатывается
локально в браузере и не отправляется на сервер.

## Работа с файлами

XML-файлы размещаются в `src/data/xml/` и включаются в сборку приложения.
Обрабатываются только файлы непосредственно в этой папке, без вложенных папок.
Выбор файлов или папки пользователем не требуется. При добавлении или изменении
XML-файлов приложение необходимо пересобрать.

## Поток данных

1. Приложение загружает XML-файлы, включённые в сборку из `src/data/xml/`.
2. Парсер извлекает элементы Teamcenter XML с учётом их пространства имён.
3. Построитель объединяет данные файлов в промежуточную модель в две фазы.
   Сначала по файлам применяются NF1–NF10: классы повторно используются по
   имени, добавляются атрибуты из `TcClass` и `TcAttributeAttach`,
   compound-свойства из `TcCompoundPropertyRule`, relation-связи из
   `TcProperty` с типом `Relation` внутри `TcStandardType` и
   `TcPropertyAttach`, GRM-правила из `TcGRMRule` и связи наследования.
   Затем по всем файлам применяется NF11: LOV-привязки из `TcLOVAttach`
   прикрепляются к построенным атрибутам со значениями из первого найденного
   `TcLOV`.
4. Маппинг задаёт отображаемый тип, имя XML-атрибута признака массива и
   перечень характеристик для каждого типа атрибута.
5. Слой раскладки преобразует модель в граф и вычисляет координаты узлов.
6. Интерфейс отображает граф и обновляет панель свойств при выборе атрибута.

Модель и построение диаграммы не зависят от React. Ошибки чтения, разбора
XML и применения маппинга должны явно отображаться пользователю.

## Интерфейс

- **Диаграмма** занимает основную область. Каждый класс — пользовательский
  узел React Flow с именем и строками атрибутов в формате `имя : тип` с `[]`
  для массивов; compound-свойства выводятся после атрибутов строками
  `имя : Compound`. Классы соединены связями наследования (сплошная линия,
  полый треугольник) и relation-связями (пунктирная стрелка от
  primary-класса к relation-классу). Класс `ImanRelation` и рёбра к нему не
  отображаются (UI6); узлы relation-классов выделены цветом (UI7).
- **Панель свойств** показывает данные выбранного атрибута,
  compound-свойства или relation-класса на вкладке Main (по умолчанию);
  вкладка LOV отображается только для атрибута с непустым списком
  LOV-привязок и выводит их по AR4. Прочие классы не выбираются. Для
  атрибута выводятся имя, отображаемый тип, признак массива и непустые
  характеристики согласно маппингу и AR1; для compound-свойства — имя, тип и
  характеристики согласно AR2; для relation-класса — имя и GRM-правила
  согласно AR3. Характеристики не выводятся в узле класса.
- **Сообщения об ошибках** отображаются в интерфейсе.

```text
project/
├── spec/
│   ├── design.md
│   ├── requirements.md
│   ├── model.md
│   └── mapping.yaml
├── examples/
├── src/
│   ├── app/                 # Корневой компонент и состояние приложения
│   ├── components/
│   │   ├── diagram/         # Диаграмма, узлы классов и связи
│   │   └── properties/      # Панель свойств
│   ├── data/
│   │   └── xml/             # XML-файлы, включаемые в сборку
│   ├── model/               # Типы, разбор XML, маппинг и построение модели
│   ├── layout/              # Раскладка графа через ELK.js
│   ├── main.tsx             # Точка входа
│   └── styles.css
├── index.html
├── package.json
├── tsconfig.json
└── vite.config.ts
```

Это целевая структура; файлы приложения создаются при реализации. Если для
реализации потребуется расширить промежуточную модель, изменения нужно
отразить в [model.md](./model.md).

## Принятые решения

Правила обработки некорректного входа определены в requirements.md (IV1–IV4):

- Повторное определение атрибута с одним именем в пределах класса — инвалидный
  вход (IV1). Конфликт двух разных непустых `parentClassName` одного класса —
  инвалидный вход (IV2); пустой или отсутствующий родитель не конфликтует с
  заданным. Повторное объявление одной пары «primary-класс → relation-класс» —
  инвалидный вход (IV5). Повтор GRM-правила с одним составным идентификатором
  (primaryTypeName + secondaryTypeName + conditionName) у одного
  relation-класса — инвалидный вход (IV6). Повтор LOV-привязки с одним
  составным идентификатором (атрибут + lovName + conditionName) — инвалидный
  вход (IV7). Во всех случаях построение модели
  прерывается, и пользователю отображается только сообщение об ошибке с
  указанием класса и повторяющегося свойства, конфликтующих родителей либо
  повторяющейся relation-связи, GRM-правила или LOV-привязки (IV4).
- LOV-привязки к ненайденным классам или атрибутам молча пропускаются;
  привязка без определения `TcLOV` сохраняется без значений, и панель
  показывает сообщение «LOV not found» (NF11, AR4).
- Атрибуты с типом, отсутствующим в `mapping.yaml`, молча пропускаются и не
  попадают в модель, диаграмму и панель свойств (IV3).
